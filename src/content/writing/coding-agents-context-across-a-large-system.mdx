In the system I was working on, repository-level context stopped being enough once tasks crossed
service boundaries. It could read every file and still miss the things
nobody had written down: intent, ownership, which invariants were actually enforced rather than
just assumed, and why the last three people hadn’t done the obvious thing.

## What was missing was mostly implicit

The things the engineers around me held in their heads on day 200 and not on day 1:

- which boundaries were real and which were accidental;
- what was load-bearing versus what was vestigial;
- which invariants were enforced in code, and which only by convention;
- what a change here tended to break over there.

<Callout type="failed">
  I spent a while trying to recover this from the codebase automatically — call graphs, commit
  archaeology, ownership heuristics. It produced something that looked like a system model and
  behaved like noise. The signal that mattered was never written down anywhere I could read it.
</Callout>

So I started writing parts of it down explicitly, as a thin artefact next to the code rather than a
document that rots in a wiki. That’s early, and I don’t know yet whether it survives contact with a
system that changes weekly. Ask me in six months.
