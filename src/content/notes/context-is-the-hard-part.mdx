Every time I’ve watched an agent fail on a real system, the postmortem has landed in the same
place. The model could reason. It just didn’t have the right things in front of it, and nothing in
the system knew that.

## The failure doesn’t announce itself

A reasoning failure looks like a reasoning failure. A context failure looks like a confident,
plausible, wrong answer — which is much worse, because the output has the same shape as a good one.

<Callout type="surprise">
  The runs that worried me most weren’t the ones that failed loudly. They were the ones that
  produced something reasonable from a partial picture and gave no signal that the picture was
  partial.
</Callout>

## More tokens is not more understanding

The reflex is to widen the window. It helps, up to a point, and then it stops helping in a way
that’s hard to notice:

- retrieval that’s *topically* relevant but structurally irrelevant;
- three versions of the same fact, one of them stale;
- everything the system knows, and nothing about what matters.

What actually moved the needle was treating context assembly as its own component with its own
contract — something I can test:

```python
# The unit under test isn’t the model. It’s what reaches the model.
def test_migration_context_includes_owning_service():
    ctx = assemble(task="rename column", entity="orders.customer_ref")
    assert ctx.includes_schema_owner()
    assert ctx.excludes_unrelated_services()
```

Once context assembly is a testable thing, the questions get sharper. Not "is the model good
enough", but "did the right five facts reach it, and how would I know".

> The interesting work isn’t the prompt. It’s everything that decides what the prompt gets to say.

<Callout type="hypothesis">
  The ceiling on most AI-enabled systems right now is context engineering, not model capability —
  and that ceiling is a systems problem, not a prompting one.
</Callout>

I’m not sure how far this generalises beyond the systems I’ve worked on. It’s what I currently
believe.
